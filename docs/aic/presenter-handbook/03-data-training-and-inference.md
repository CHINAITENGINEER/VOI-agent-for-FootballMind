### 1.3 状态转移数据需要什么

| 需求项 | 实际字段 | 状态 |
|---|---|---|
| 对应比赛 | `physical_match_id` | ✅ |
| 当前已采用的证据集合 | 序列中的 `adopted_ids` | ✅ |
| 当前预测概率 | `p_before`（由冻结 f 重算） | ✅ |
| 当前候选正文 | `candidate_scores[].document_id` | ✅ |
| 候选是否被采用 | `selected_ids` / `unselected_ids` | ✅ |
| 采用前后的预测结果 | `p_before` / `p_after` | ✅ |
| 对应真实赛果 | `outcomes.jsonl`（**只在结算层读取**） | ✅ |
| 收益标签如何计算 | `Δ_f = log p_after(Y) − log p_before(Y)` | ✅ |
| 属于哪个数据划分 | `split_role` | ✅ |

### 1.4 目标绑定规则（重要，防止"猜关联"）

schema 明文规定：

> `target_binding_rule`: **"Saved structure/explicit aliases lexical mentions and saved registry owner only; no URL/name guessing; no outcome or f output."**

也就是说：
- 只使用**已保存的结构、显式别名、词面提及、注册表归属**；
- **不猜 URL，不猜队名，不使用赛果或 f 的输出**。

**这条规则的意义**：防止"看起来像"的关联被当成真实关联。


## 阶段三：文章关联与标注

### 3.1 文章如何与比赛和实体关联

按 1.4 的规则执行：**已保存结构 + 显式别名 + 词面提及 + 注册表归属**。

`schema.json` 的 `claim_relation_semantics` 有一句关键限定：

> **"exact claims / availability multistatus only; not truth or contradiction; missing claims unknown; factual_update_unknown always 1"**

**这意味着**：
- 系统记录的是"**出现过哪些断言**"，**不是"断言是否为真"**；
- 也**不是"断言之间是否矛盾"**；
- 缺失就是未知，**不推断**。

### 3.2 四个概念必须严格区分（贯穿全文）

| 概念 | 定义 | 本项目是否建模 |
|---|---|---|
| **相关性** | 文章与这场比赛有关吗？ | 部分（元数据里有队名提及计数、目标别名匹配度） |
| **真实性** | 文章说的事是真的吗？ | ❌ **不建模**。schema 明说 `not truth or contradiction` |
| **预测增益** Δ_f | 采用它之后同一个 f 的损失改善多少？ | ✅ **这是核心监督目标** |
| **经济收益** | 实际赚了多少钱？ | ❌ **不定义**（无投资组合、无交易成本模型） |

**答辩时必须能说出这句话**：
> 我们建模的**只有第四个概念之前的第三个**——预测增益。我们**不判断真伪**，schema 里明确写了只记录"出现过哪些断言"，不判断"断言是否为真"。我们**也不计算经济收益**。

### 3.3 来源冲突、重复报道与缺失信息如何处理

| 情形 | 旧版机制 | 新版处理 |
|---|---|---|
| **重复正文** | `_digest` 去重 | `document_id = sha256(正文)` → 天然去重 |
| **同源同实体的后继文档** | 旧版有"超越规则"：要求同 `source_host`、不同 `document_url`、时间更晚、且所有候选值一致 | 新版有元数据列 `exact_prior_body_duplicate`、`repeated_claim_count` |
| **多状态冲突** | 旧版保留为 `unresolved_source_disagreement`，**不静默裁决** | 新版有 `existing_multistatus_count`、`candidate_introduced_multistatus_count`、`candidate_expanded_multistatus_count` |
| **缺失信息** | 保留为未知 | `*_unknown` 系列布尔列，**缺失即标记，不推断** |

**必须知道的口径**：新版语料里 `candidate_expanded_multistatus_count` 的非零行为 **0**，`candidate_introduced_multistatus_count` 非零行为 **7**，`existing_multistatus_count` 非零行 **6**，`repeated_claim_count` 非零行 **16**。这些数字都很小，说明**冲突与重复在合格语料里是低频事件**。

### 3.4 关于"强模型预标注"（必须如实区分版本）

这是答辩者最容易被问倒的地方。**准确答案是：**

| 版本 | 是否使用强模型预标注 | 说明 |
|---|---|---|
| **旧版在线原型** | ✅ 使用 | 接入 **DeepSeek Chat Completions**，用于**语义抽取与分类**（把正文分类为 `supports / refutes / no_answer`）。旧版报告的 runbook 中记录了 provider 配置 |
| **新版全文序列研究** | ❌ **不使用** | 神经模型**直接读取全文向量**，不依赖任何 claim 抽取。schema 明写 `no_claims_requirement = true` |

**新版的事实支撑**：
- 3,001 篇中 **2,915 篇无结构化 claims**；主序列语料里只有 **86 篇**有已知 claims。
- 报告原话："**神经模型仍读取这些完整正文，未因缺 claim 把向量置零。**"

**所以准确表述是**：
> 新版的全文模型**不使用任何强模型预标注**——它直接读全文向量。claim 抽取是**旧版在线原型**的机制，新版继承下来只作为元数据列（且 97% 为未知）。

**如果被问"强模型预标注会不会引入偏差"**，正确答案：
> 这个问题在**旧版**适用——旧版用 DeepSeek 做语义分类，它可能把推断写成原文事实，所以旧版专门设计了四项门控来防这一点（方向、主体、方向依据、逐字引文四项必须同时成立）。**新版不走这条路**：新版不做 claim 抽取，直接读全文，风险从"抽取错误"变成"监督信号不足"。

### 3.5 是否有 Argilla 等人工标注工具

**未找到原始证据。** 本文件不假设项目使用过 Argilla 或任何标注平台。已核实的人工介入环节是：

| 环节 | 方式 | 证据 |
|---|---|---|
| 字段定义与掩码设计 | 人工设计 | `schema.json`、`model.json` |
| 阈值候选集 | 人工预设 `[-0.01, -0.003, 0, 0.003, 0.01]` | `bundle-config.json` |
| 早期 C 集菜单判读 | **单标注者 + 规则公开 + 边界项敏感性分析** | `bench\menu_labels.json` |
| 早期双标注 | ❌ 未做 | 报告自述"没有做人工双标注" |

## 阶段四：Embedding 与样本构造

### 4.1 完整流程

```
原始正文（UTF-8 原样，无标题注入、无截断）
    │
    ▼
document_id = sha256(正文)          ← 天然去重
    │
    ▼
冻结 Qwen3-Embedding-0.6B
  · revision 97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3
  · pooling: last_nonpadding_token
  · normalization: l2 → matryoshka prefix → l2
    │
    ▼
原生 1024 维 ──► 取前 256 维 ──► L2 归一化
    │
    ├─► 【f 的输入】已采用正文的 256 维向量集合 + 16 维生效元数据 + s0 先验
    │
    └─► 【g 的输入】1140 维 = 状态 349 + 候选 256 + 差 256 + 积 256 + 元数据 22 + 相似度 1
```

### 4.2 逐项解释

**为什么用 Qwen3-Embedding-0.6B**：它是当前开源 0.6B 级中较强的文本嵌入模型之一，**且不需要训练**。在只有 294 场正文监督的条件下，用冻结的预训练表示替代从零训练，是唯一可行的选择。

**哪些参数冻结**：全部 595,776,512 个参数。项目本轮训练的参数量**不含编码器**。

**向量维度**：原生 **1024**；项目使用前 **256** 维。**没有下游投影层**——256 维是通过 Matryoshka 前缀截取 + 重新 L2 得到的。

**当前状态如何进入模型**：
- 进入 f：`p_s0`（3 维先验）+ 已采用向量的集合表示
- 进入 g：`current_f_probabilities`（3）+ `entropy`（1）+ `adopted_count`（1）+ `remaining_count`（1）+ `remaining_budget`（1）+ `adopted_mean_embedding`（256）+ `adopted_mean_metadata`（22）+ `current_f_hidden_state`（64）= **349 维**

**候选全文如何与历史证据表示结合**：
- 不合并，而是**并列给出**：候选 256 + 已采用均值 256 + 绝对差 256 + 逐元素积 256
- 这样 g 能分别看到"候选是什么""已读过什么""差在哪""哪里重叠"

**为什么相同正文在不同状态下 Δ_f 不同**：
因为 `L_before` 是状态的函数。已采用集合越大，边际贡献越小；与已有证据重复时 Δ_f 接近 0。

### 4.3 必须核实的配置（已核实）

| 项 | 值 | 来源 |
|---|---|---|
| 编码器 revision | `97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3` | `encoder-provenance.json` |
| 编码器权重 SHA | `0437e45c94563b09e13cb7a64478fc406947a93cb34a7e05870fc8dcd48e23fd` | 同上 |
| dtype | `float32` | 同上 |
| token 上限 | 短契约 8192 / 长契约 32768 | 同上 |
| 向量来源计数 | 既有本地 CPU 缓存 1,712 + 冻结交接 CPU 对照 8 + 验证通过的 GPU 结果 1,286 | `research-delivery-v1\readable-report.txt` |
| 编码器在新版是否被训练 | ❌ **否** | `model_checkpoint_modified: false` |

## 阶段五：训练预测器 f

### 5.1 一步一步

| 步 | 动作 | 细节 |
|---|---|---|
| 1 | 构造训练样本 | 用 `sequences.jsonl`；每场包含 s0、s1、s2… 的输入与标签 |
| 2 | 输入特征 | 已采用正文的 256 维向量 + 16 维生效元数据 + s0 先验 |
| 3 | 监督标签 | **历史赛果**（三分类） |
| 4 | 组织每场的证据状态 | 集合式：已采用向量构成置换不变的集合；GRU：按顺序逐步输入 |
| 5 | 损失函数 | 交叉熵 |
| 6 | 权重分配 | **先对每场全部前缀平均（含空前缀 s0），再对所有比赛等权** |
| 7 | 训练/开发评估 | 训练用 f_train 294 场；**检查点由 f_dev 74 场的 `match_balanced_prefix_log_loss` 选** |
| 8 | 确定配置 | 优化器 AdamW lr 0.001 / wd 0.01 / betas [0.9,0.999] / eps 1e-8 / grad clip 5.0；batch 32 场比赛；最多 200 epoch；patience 25；3 seed（11/29/47） |
| 9 | 冻结参数 | `parameter_updates_during_predict = false`；导出前恢复检查点 |
| 10 | 保存与复现记录 | `model.json` 记录 f SHA、源文件哈希、软件版本（torch 2.11.0+cpu、numpy 2.3.5） |

### 5.2 四个必须回答的问题

**① 训练 f 的数据是否包含真实赛果？**
✅ **包含。** 赛果是训练标签。

**② 真实赛果是否可能泄漏进赛前预测输入？**
❌ **不会。** 三重保障：
- `label_usage = "training and evaluation only; excluded from prediction arguments"`
- schema 的 `target_fields_never_embedding_input` 显式列出 **`outcome_class`、`gain`、`p_after`**
- 数据验证检查 `empty_prefix_retained`、`metadata_exact_reproduction` 等 13 项全部通过

**③ f 是否在训练阶段使用候选正文的实际收益标签？**
❌ **不使用。** f 的标签是**赛果**，不是 Δ_f。Δ_f 是给 g 用的标签。

**④ 为什么生成 g 的标签时必须固定 f？**
因为 Δ_f 的**前后两次预测必须用完全相同的参数**。否则损失差里混入了"换模型"的效果，无法归因给正文。这就是"冻结"的意义。

### 5.3 数据验证清单（13 项全通过）

| 检查 | 含义 |

| `empty_prefix_retained` | **空前缀被保留**（s0 未丢） |
| `f_dev_before_gfit` | f_dev 早于 g_fit（时间顺序正确） |
| `link_meta_matches_schema` | 链接元数据匹配 schema |

**答辩提示**：这 13 项是"**数据构造的自检**"，不是"模型效果好"的证据。要分清。

## 阶段六：生成 g 的监督标签（**核心章节**）

### 6.1 完整流程

```
① 选定对应版本的预测器 f
        │
② 冻结 f 的全部参数
        │
③ 读取一个历史比赛的当前证据状态 s（含 s0、s1、s2…）
        │
④ 计算当前预测 p_before 与损失 L_before = −log p_before(Y)
        │
⑤ 把候选正文 a 加入状态 → s'，重算 p_after
        L_after = −log p_after(Y)
        │
⑥ 生成标签 Δ_f = L_before − L_after
        │
⑦ 保存：候选正文、当前状态、预测器版本、标签
        │
⑧ 用这些样本训练对应版本的 g
        │
⑨ 在 g_dev 上选配置与阈值
        │
⑩ 在 validation / test 上评估完整策略
```

### 6.2 公式与逐项解释

```
Δ_f = L_before − L_after

当 L = −log p_f(Y) 时：
Δ_f = log p_after(Y) − log p_before(Y)
```

| 符号 | 含义 | 本项目具体所指 |
|---|---|---|
| `f` | **某一个具体的、冻结的**预测器 | `set_residual_mlp-seed47`（SHA `b36b2cf8…`）或 GRU |
| `Y` | 历史真实赛果 | `outcomes.jsonl`，只在训练与结算使用 |
| `L_before` | 采用候选前的损失 | 基于当前状态前缀 |
| `L_after` | 采用候选后的损失 | 把候选向量加入已采用集合后重算 |
| `Δ_f` | 预测评分改善量 | 正 / 零 / 负 |

### 6.3 三类标签

| 符号 | 含义 | 集合 f 侧实际数量 |
|---|---|---:|
| **正** | 采用后评分改善 | **5,904** |
| **零** | 无变化 | **0** |
| **负** | 采用后评分变差 | **4,542** |

**必须能解释"零为什么是 0"**：
报告原话："**零样本计数为 0 是本轮有效标签的实际结果，代码未筛除零或负收益。**"因为标签是在连续概率空间上算的差值，恰好等于零的概率极低。而负标签有 4,542 条——**"读一篇新闻反而变差"是常态**。

**另一个必须能解释的数字**：`failure_rows = 4,540`。报告明确：

> "**4,540 条失败清单都是 `input_preparation / sequence_not_eligible`，不是 4,540 次 f 执行失败**；gain = null。"

### 6.4 三个必须同时说出的限定

1. **Δ_f 是经验预测增益的监督定义，不是已经证明的因果效应。**
2. **Δ_f 不等于实际经济收益。** 它是 log loss 的改善，不是钱。
3. **Δ_f 依赖具体的 f。** 换 f 就必须重新生成标签。

### 6.5 版本隔离（不得合并）

| | 旧版 g | 新版 g |
|---|---|---|
| 标签来源 | 旧版 f（实体证据型） | 新版 f（全文序列型） |
| 输入维度 | 15 个关系特征 + 标题 TF-IDF | **1140 维**（含全文向量） |
| 标签定义 | `signed_gain`（同一旧 f 前后差） | `Δ_f`（同一新 f 前后差） |
| 是否复用 | ❌ `not_reused_across_incompatible_f_binding` | — |

**⚠️ 绝对不能把旧版与新版的训练过程合并成一个"统一流程"。**

## 阶段八：完整策略评估

### 8.1 为什么不能只看 g 的回归误差

因为**回归误差小 ≠ 策略表现好**。两个原因：
- g 的价值体现在"该不该采用"这个**决策**上，MSE 无法反映阈值选择质量；
- 用户最终看到的是**预测损失**，不是中间层误差。

### 8.2 实验条件

同一比赛集合 ｜ 同一候选池 ｜ **固定同一个 f** ｜ **采用预算 = 3 篇** ｜ 指标 = 逐场等权平均 Log Loss（越低越好）｜ 随机策略每场 10 个 seed 先平均，再按比赛等权。

### 8.3 结果（集合 f 配套，已逐位核对）

| 策略 | 验证集 193 场 | 测试集 320 场 |
|---|---:|---:|
| 不采用正文（校准先验） | 0.963980 | 1.022476 |
| 固定顺序 | 0.962062 | 1.022446 |
| 随机采用 | 0.962063 | 1.022450 |
| **state-Ridge g（开发集选定）** | **0.963420** | **1.021563** |
| 原始市场参考 | 0.965245 | **1.020413** |

### 8.4 四条必须同时说出的读法

**① 验证集上 state-Ridge 没有超过固定顺序与随机。**
0.963420 > 0.962062（固定）> 0.962063（随机）。**在验证集上它并不占优。**

**② 测试集上点估计最低，但区间包含 0。**
state-Ridge 1.021563 是所有内部策略里最低的，比随机（1.022450）低约 **万分之九**。但配对 bootstrap（比赛为抽样单元、2,000 次、seed 20261025）给出：

| 对比 | 差值 | 95% 区间 | 结论 |
|---|---:|---|---|
| set / validation：新 g − 随机 | **+0.001357** | [−0.000466, +0.003016] | 跨 0，且点估计为**正**（更差） |
| set / test：新 g − 随机 | **−0.000886** | [−0.002299, +0.000438] | 跨 0 |

**③ 测试集上原始市场参考损失更低（1.020413）。**
但**其对照身份有限制**：`prior_time_verified = false`，报价时点未被验证。所以它是"**历史参考**"，不是"同条件的实时赛前先验"。

**④ 所以当前结论是**：
> **没有建立跨集合的稳定优势**，但得到了一套**可以继续比较和改进的完整策略评估框架**——而且这套框架能明确区分"点估计改善"和"统计上不显著"。

### 8.5 一个必须会解释的额外事实

`state_ridge` 的输入**不含候选向量**，所以**同一状态下所有候选同分**。冻结包明确记载："在 **334 个多候选决策状态**中全部候选同分，按冻结来源顺序破平；**不是全文排序模型**。"

**所以 state_ridge 的优势（若存在）来自"判断何时停止"，不来自"选择哪一篇"。**

**对比**：GRU 配套的 `local_metadata_refit_ridge` 在 test 320 场**只采用 10 次**，**115 场英超全部停止于未采用状态**。报告原话："**收益优势可能来自少读，不代表识别了更好的文章。**"

### 8.6 Log Loss 的通俗解释

Log Loss = `−log p(真实结果)` 的平均。**给真实结果的概率越低，罚得越重。**

- 如果模型给真实结果 90% 概率，罚 ≈ 0.105
- 如果给 30%，罚 ≈ 1.204
- 如果给 1%，罚 ≈ 4.605

**所以 Log Loss 越低越好**。本项目测试集在 1.02 附近，意味着平均而言模型给真实结果的概率约 36%。

## 阶段九：运行时推理

### 9.1 一场新比赛的完整过程

| 步 | 动作 | 输入 | 输出 |
|---|---|---|---|
| ① | 读取当前比赛状态 | 比赛身份 | s0 概率 + 空已采用集合 + 预算 3 |
| ② | 取得候选正文 | 冻结候选池 | 候选列表 |
| ③ | 生成全文语义表示 | 正文 | 256 维向量（**预编码缓存，不现场编码**） |
| ④ | g 评估条件预测增益 | 1140 维 | 每篇一个标量分数 |
| ⑤ | 选择策略决策 | 分数 + 阈值 + 预算 | 采用 or 停止 |
| ⑥ | 将被采用证据加入状态 | 采用编号 | 更新后的已采用集合 |
| ⑦ | f 重算概率 | 新状态 | 新三分概率 |
| ⑧ | 记录 | 采用顺序、输入 ID、概率变化 | 审计记录 |
| ⑨ | 决定下一步 | 新状态 + 剩余预算 | 回到 ④ 或停止 |
| ⑩ | **赛后单独结算** | 赛果 | loss 与 Δ_f |

### 9.2 运行时输入 vs 历史训练标签（必须分清）

| | 运行时输入 | 历史训练标签 |
|---|---|---|
| 包含赛果？ | ❌ **绝不包含** | ✅ 包含 |
| 用途 | 产生预测 | 计算 Δ_f |
| 代码保障 | `forbidden_inputs` 显式禁止，`outcomes_used_in_prediction = false` | 独立标签文件 |

### 9.3 为什么运行时不能用尚未发生的赛果

因为那**不是预测，是作弊**。项目的保障有四层：
1. `outcomes_used_in_prediction = false`（冻结运行记录里的显式标志）
2. `target_fields_never_embedding_input` 列出 `outcome_class / gain / p_after`
3. 结算层与推理层**代码分离**（`run_case` vs `settle_run`）
4. 冻结包验收记录："**prediction 期间 outcomes 读取被主动拦截且触发 0 次**"

**这第 4 条特别值得记**：它说明项目不仅"设计上禁止"，而且**在验收时实测过"拦截被触发 0 次"**——也就是说，推理路径根本没有尝试读赛果。
