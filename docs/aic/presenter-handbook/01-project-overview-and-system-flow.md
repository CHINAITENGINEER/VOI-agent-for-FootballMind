## 第一部分：先理解问题，再谈技术

### 1.1 为什么是足球赛前情报

判断一个项目是否值得研究，先看它的实验场景是否**天然具备研究所需的困难**。足球赛前情报同时满足四个条件：

| 条件 | 足球赛前情报的具体体现 |
|---|---|
| **信息开放但不完整** | 伤病、阵容、轮换意图、战术准备都写在公开报道里，但没有任何单一来源能给出完整答案 |
| **来源质量参差** | 同一件事，俱乐部官网、足协发布会、转会新闻、球迷投票文章的可靠性完全不同 |
| **判断有时效性** | 一条"某球员进行个人训练"的报道，在赛前三天和赛前一小时的含义完全不同 |
| **结果可事后核验** | 比赛有客观、唯一、公开的赛果，因此任何赛前判断都能被事后评分 |

**这四条合起来，让足球成为一个"可以严谨做实验"的动态决策环境**——而不是一个只能讲故事的应用场景。

### 1.2 普通预测模型在做什么，缺了什么

一个普通的足球预测模型长这样：

```
输入：固定的特征表（球队历史战绩、Elo、xG、主场优势……）
输出：主胜 / 平局 / 客胜 的概率分布
```

它的问题不在于精度，而在于**它是静态的**：给定一场比赛，它读一次输入就给出一个答案，不会问"我还缺什么"。

而在真实环境里，赛前 24 小时里会发生这些事：

- 教练在发布会上说某主力"这场可能休息"；
- 官网发了一篇训练报道，但没提阵容；
- 一篇看起来相关的文章其实是**去年同一对阵**的旧稿；
- 你读到的第一篇只说明"某球员正在康复训练"——这既不是"会出场"，也不是"会缺阵"。

**所以真正的问题不是"能不能预测"，而是**：

> **当系统已经有了一个初始判断，新信息不断出现时，它怎么判断哪条信息值得采用、采用之后可能带来什么预测变化、以及什么时候应该停止？**

这就是 FootballMind 的研究问题。**它不是"比分预测器"，也不是"新闻摘要工具"。**

### 1.3 六个"为什么"，把问题链讲透

**① 为什么候选新闻与当前判断之间存在"增量价值"问题？**

因为同一篇正文的价值取决于**你当前已经知道什么**。

举例：如果系统已经读了首发阵容公告，再读一篇转述首发名单的新闻，**增量几乎是零**。但如果系统还不知道阵容，同一篇新闻的增量就很大。所以"这篇文章好不好"不是一个能脱离状态回答的问题。

**② 为什么"获取到一篇新闻"不等于"应该采用它"？**

三个独立的理由：

- **相关 ≠ 有价值**：一篇赛前预览可能通篇讲历史战绩，与"本场谁首发"无关。
- **真实 ≠ 能改变概率**：一篇官方发布会报道可能只重复了已知信息，概率不该动。
- **能改变概率 ≠ 改善预测**：这是最关键的一条——采用一篇正文后概率会变化，但**变化的方向可能是错的**（实测中确实存在负增益样本）。

**③ 为什么采用证据后要重新计算概率？**

因为概率是决策的依据，而证据改变了信息状态。这一点本身是贝叶斯更新的常识，项目的增量不在这里，而在于**如何判断该不该更新、以及更新是否值得**。

**④ 为什么还需要"继续处理还是停止"的决策？**

因为获取和阅读都有成本。项目在运行时设置了硬预算（旧版在线原型：最多 10 次来源请求、5 次正文读取、5 次模型调用、15 分钟超时、每轮最多批准 2 个新域名）。当所有候选的预期增益都低于阈值时，系统应该停止——**而不是为了"读得更多"而继续消耗**。

**⑤ 为什么需要对全过程记录和复核？**

因为"概率变了"这个说法本身无法被检验。只有把**采用编号、输入证据、采用前后概率、停止原因**全部落盘，别人才可能复算你的结论。项目的冻结演示包做到了这一点：160 场默认轨迹逐条复算一致。

## 第二部分：用一个真实案例贯穿全流程

**贯穿案例：Brentford vs Arsenal，2025-01-01**（新版全文模型历史重算，也是演示包的默认案例）

### 2.1 案例三组概率（已回到冻结产物核对）

| 阶段 | 主胜 | 平局 | 客胜 |
|---|---:|---:|---:|
| 原始市场参考 | 14.24% | 19.79% | 65.97% |
| **空证据预测器 f（s0）** | 12.95% | 19.39% | 67.65% |
| **采用 1 篇正文后** | 13.41% | 20.01% | 66.58% |

**两句必须同时说出口的话**：
1. **原始市场参考与空证据 f 之间的差异，不是正文带来的增益。** f 的 s0 本身已经是"校准后的市场先验"，它和原始市场报价之间的差距来自**校准器**，不是来自新闻。
2. **概率变化是模型响应的直接证据，不等于预测质量已经改善。** 本例实算 Δ_f = **−0.015919**（在本场，采用这篇正文使正确结果的对数概率略微下降）。

### 2.2 候选池与选择过程（已核对原始记录）

当天冻结候选池有 **5 篇**正文，全部来自 `arsenal.com`：

| # | 文章（简化标题） | g 给出的分数 | 是否采用 |
|---:|---|---:|---|
| 1 | inside-training-preparing-to-take-on-brentford | 0.006819 | 否 |
| 2 | **pick-your-mens-player-of-the-month-for-december** | **0.014555** | **是**（超过阈值 0.01） |
| 3 | arteta-on-squad-rotation-for-brentford | **−0.000924** | 否（分数最低） |
| 4 | timber-on-2024-brentford-and-more | 0.011135 | 否 |
| 5 | preview-brentford-v-arsenal | 0.007537 | 否 |

采用的停止原因是 `predicted_gain_below_frozen_threshold`（下一轮所有候选的预测增益都低于冻结阈值 0.01）。

**这个案例必须如实讲，不能美化**：
- 实际被采用的是**月度最佳球员投票文章**——一篇球迷投票稿。**绝不能为了让案例更有说服力而改成伤停新闻。**
- 而候选里那篇听起来最相关的"关于轮换的采访"，得分反而**最低**。

**这个"不完美"恰恰是案例最有价值的地方**：它说明 g 目前的判断与人的直觉不一致。这直接引出第 9 页的实验——**单场判断不可靠，必须做全量策略评估**。

| 环节 | 发生了什么 | 用什么算法 | 代码 / 数据 |

```
│        │        │                                                                    │

│        │                                    │                                        │

└──────────────────────────────────────────────────────────────────────────────────────┘

```

**绘制时必须遵守的三条**：
1. **离线训练与运行时推理必须分区**，不要把训练模块画进单场循环。
2. **第 ⑩ 步结算层必须与第 ①–⑨ 步分开**——赛果只在结算时读取，绝不进入赛前推理。
3. **不要画入通用 Agent、自主研究模块、跨领域能力**——这些没有实现。

### 3.2 三层职责划分（这是一句关键澄清）

| 组件 | 角色 | 用一句话说 |
|---|---|---|
| **g** | **估计** | 结合候选全文、当前预测与已有证据状态，给出该候选的**条件预测增益**估计 |
| **选择策略** | **决定** | 依据 g 的评分与预算，决定**采用或停止**。这一步是策略执行的，**不是 g 单独完成** |
| **f** | **响应** | 依据**已采用的**证据重新计算胜平负概率 |

> 评委如果问"是不是 g 决定了一切"，正确答案是：**不是。g 只给分数，采用/停止由策略按阈值与预算执行。**

## 第四部分：把算法讲在流程里（这是本文件的核心）

下面每一小节都按同一格式：**为什么需要 → 用什么算法 → 输入输出 → 在我们这里有什么证据 → 评委可能追问**。

### 4.1 在"全文编码"处：Embedding 是什么，为什么用它

**为什么需要？** 神经网络不能直接吃一段英文文本。而且如果把 3,000 篇正文全部展开成词表，每篇会变成几万个稀疏维度，样本量根本撑不住。

**用什么算法？** 冻结的 **Qwen3-Embedding-0.6B**（5.96 亿参数）。它把一段正文压成一个固定长度向量，**语义相近的文本向量距离近**。

**输入输出**：全文原样输入（不注入标题、不截断、不加提示词）→ last-nonpadding pooling → 原生 **1024** 维 → 项目取**前 256 维**再 L2 归一化（Matryoshka 前缀截取）。

**为什么冻结、不微调？** 因为训练数据只有 294 场 / 521 篇。在这个规模上微调一个大编码器，最大风险是**把来源身份当作捷径学进去**（早期实验已经量化过这个风险：把标题替换成常数，测试误差反而下降）。冻结 = 承认样本量不足，用先验知识代替训练。

**它在这里做什么**：给 f 和 g 提供 256 维语义输入。

**⚠️ 语义相似度 ≠ 预测价值**：向量能告诉你"这两段文字在讲同一类事"，但**不能**告诉你"这篇报道会不会改变本场胜负概率"。后者需要监督标签（见 4.3）。

**评委可能追问**：
- *"为什么不全用 1024 维？"* → 预测头取前 256 维是 Matryoshka 性质；在 294 场的监督量上，压缩后的容量匹配更合适。要如实说：**没有做过 1024 维 vs 256 维的头对头对照**，所以这是一个配置选择而非已验证结论。
- *"为什么不微调？"* → 样本量 + 捷径风险，如上。

### 4.2 在"预测器 f"处：它到底算什么

**f 的数学定义**：f 是一个从证据集合到概率分布的映射

```
f : (已采用正文集合 S，比赛元数据 M) → p = (p_home, p_draw, p_away)
```

**输入包含什么**（已核对 `models\f\model.json`）：
- 每篇已采用正文的 **256 维**语义向量（集合表示，置换不变）
- **16 维生效元数据**：`log1p_days_before_match`、`publication_time_unknown`、`historical_version_unknown`、`source_is_official`、`log1p_body_characters`、`historical_reconstruction`、`candidate_claims_unknown`、`factual_update_unknown`、`source_official_unknown`、`exact_home_team_mentions`、`exact_away_team_mentions`、`target_aliases_unknown`、`target_aliases_partial`、`source_target_home`、`source_target_away`、`source_target_unknown`
- **s0 先验**（校准后的市场概率）

**输出为什么是三分类概率**：这是本项目唯一的预测对象——常规时间主胜 / 平局 / 客胜。

**训练标签与损失**：标签是**历史赛果**（三分类）。损失是交叉熵，**先对每场比赛的全部前缀平均（含 s0），再对所有比赛等权**。

**为什么"先平均前缀、再按比赛等权"**：因为一场比赛可以对应很多篇正文和很多个前缀。如果直接对所有前缀平均，**正文多的比赛会被过度加权**。按比赛等权才能让每场比赛贡献相同的权重。

**两种 f 的区别**：

| | 集合残差 MLP | GRU |
|---|---|---|
| 处理已采用证据的方式 | 把已采用向量当作**集合**，置换不变 | 把证据当作**序列**，逐步更新隐状态 |
| 参数量 | 26,823 | 67,079（隐状态 64） |
| 结构含义 | "读了哪几篇" | "按什么顺序读的" |

**"残差"是什么意思**：初始残差头为零，所以第 0 个 epoch 的输出**恰好等于冻结的校准先验**。模型学的不是"从零预测概率"，而是"在已有一个先验的基础上，文本应该带来多少修正"。

**如何得到采用前后的概率**：以 s0 为起点，采用第 1 篇后重算得 p_1，再采用第 2 篇得 p_2……每一步都落盘。

**为什么训练标签与赛前输入必须分离**：`parameter_updates_during_predict = false`，且赛果 `label_usage = "training and evaluation only; excluded from prediction arguments"`。这是硬约束，不是习惯。

**评委可能追问**：
- *"为什么 best_epoch 是 1？"* → **如实回答**：在 f_dev 上选出的检查点是第 1 个 epoch，说明在当前监督信号下继续训练不能改善开发集损失。这指向"文本监督信号不足"，而不是"训练出错了"。
- *"集合和 GRU 哪个更好？"* → 分集合看：**f_dev 上 GRU 更好（0.958916 < 0.962041），test 上集合更好（1.022482 < 1.026598）**。**不能声称 GRU 更优。** 报告还说明两者的元数据使用存在差异，所以差异不能纯归因于循环结构。

### 4.3 在"信息价值估计"处：g 为什么存在，它学什么

**为什么需要单独一个 g？** 因为 f 只会"算出概率"，不会"判断哪一篇值得读"。如果没有 g，系统只能：要么全读（成本高、且可能引入负增益），要么按固定顺序读（与内容无关）。

**这是一个监督学习问题吗？** 是。目标值就是 4.4 节定义的 Δ_f。

**g 的输入**：1140 维（见 [08](08-data-dictionary-and-version-map.md) §3.2 的完整分块表）。三个设计要点：
- 候选向量（256 维）与**已采用均值**（256 维）同时给出；
- **绝对差**（256 维）与**逐元素积**（256 维）——让模型能表达"这篇和已读的是**互补**还是**重复**"；
- 状态里的 **f 隐状态（64 维）**——让 g 知道 f 当前"是怎么想的"。

**g 的输出**：一个标量分数，含义是**"在当前状态下采用这一篇预计能带来多少 Δ_f"**。

**一个必须讲清楚的区别**：

| 概念 | 是什么 |
|---|---|
| **相关性** | 这篇文章与这场比赛有关吗？ |
| **真实性** | 文章说的事是真的吗？ |
| **预测增益 Δ_f** | 采用它之后，**同一个 f** 的预测损失改善了多少？ |
| **经济收益** | 采用它之后，实际赚了多少钱？ |

**g 只学第三个。** 它**不是**真实博彩收益模型。这是评委最容易攻击的点，必须主动澄清。

**为什么 g 必须与对应的 f 绑定**：因为标签 Δ_f 是**用某个具体的 f 算出来的**。换一个 f，同一篇正文的 Δ_f 就不同。旧版 g 的状态在模型资产表里明确记录为 `not_reused_across_incompatible_f_binding`——**不能跨 f 版本复用 g**。

**Ridge、state_ridge、MLP 的区别**（都要讲清）：

| 头 | 输入 | 能不能给候选排序 | 说明 |
|---|---|---|---|
| `state_ridge`（350 参数） | **349 维状态，不含候选向量** | ❌ **不能**——同一状态下所有候选同分 | 它实际学的是"**继续还是停止**" |
| `fulltext_ridge`（1141 参数） | 1140 维（含候选向量） | ✅ 可以 | 线性排序器 |
| `fulltext_mlp`（154,369 参数） | 1140 维 | ✅ 可以 | 非线性排序器 |
| `zero` / `train_mean` | 常数 | ❌ | 基线 |

**"近常数化"是什么意思，说明了什么**：

在 g_dev 的回归指标里，`state_ridge` 的 Spearman 相关只有 **0.0096**（≈ 0）——也就是说，它的预测分数与真实增益几乎**没有秩相关**。而在 g_fit（训练侧）上它的 Spearman 是 **0.2213**。

**这说明什么**：
- ✅ 说明**在开发集上，这个头的排序能力消失**——训练侧有的信号没有迁移到开发集。
- ✅ 说明**训练—评估落差是真实存在的**（另一个直接证据：全文 MLP 在 g_fit 上 macro MSE 0.0000067，在 g_dev 上 0.000181，在 test 上 0.000252）。

**不能说明什么**：
- ❌ 不能说明"所有信息价值估计方法都无效"——只测了 7 个头、1 个标签定义、1 个数据规模。
- ❌ 不能说明"g 的精度是 X"——不同头的目标不完全相同（state_ridge 无排序能力是**设计使然**，不是缺陷）。

**评委可能追问**：
- *"既然 state_ridge 不会排序，为什么选它？"* → 因为它**不是按排序能力选的，而是按 g_dev 上的完整策略损失选的**。它的作用是在合适的时机停止。这一点在冻结包的 `bundle-config.json` 里写得很明确。
- *"那你们到底有没有会排序的 g？"* → 有，`fulltext_ridge` 和三个 `fulltext_mlp` 都能排序。但**它们未证明在完整策略上优于随机**（见第 9 页实验）。

### 4.4 在"标签生成"处：条件预测增益的完整定义

**公式**

```
Δ_f = L_before − L_after
```

当损失取负对数似然 `L = −log p_f(Y)` 时：

```
Δ_f = log p_after(Y) − log p_before(Y)
```

**逐项解释（每个符号都要能解释）**：

| 符号 | 含义 |
|---|---|
| `f` | **某一个具体的、冻结的**预测器版本 |
| `Y` | 该场历史的**真实赛果**（主胜/平局/客胜），只用于监督与结算 |
| `L_before` | 采用候选正文**之前**，f 在该场上的预测损失 |
| `L_after` | 把候选正文加入证据后，**同一个 f** 重新预测得到的损失 |
| `Δ_f` | 预测评分的改善量 |

**三类标签各代表什么**：

| 符号 | 含义 | 项目中的实际数量（集合 f 侧，g_fit+g_dev） |
|---|---|---:|
| **正** | 采用后预测评分**改善** | **5,904** |
| **零** | 没有变化 | **0** |
| **负** | 采用后预测评分**变差** | **4,542** |

> **"零标签为 0"这个数字要会解释**：报告写明"零样本计数为 0 是本轮有效标签的实际结果，**代码未筛除零或负收益**"。因为本项目的标签是在连续概率空间上算的，恰好等于零的概率极低。而**负标签有 4,542 条**，说明"读一篇新闻反而变差"是常态，不是异常。

**为什么同一篇正文在不同状态下 Δ_f 不同**：因为 `L_before` 取决于当前已有证据。已有证据越多，这篇的边际贡献越小；如果这篇与已有证据重复，Δ_f 会接近或等于零。

**为什么必须固定同一个 f 比较**：如果采用前后用了不同的预测器，损失差里就混入了"换模型"的效果，无法归因给这篇正文。项目的硬约束：f 参数在对外的推理调用中**永不更新**。

**⚠️ 三条必须同时说出的限定**：
1. Δ_f 是**经验预测增益**，**不是已经证明的因果效应**。
2. Δ_f **不等于实际经济收益**——它是 log loss 的改善量，不是钱。
3. Δ_f 依赖**具体某个 f**；换 f 就换标签。

**评委可能追问**：
- *"为什么保留负标签？"* → 因为删掉负标签会让 g 学到"任何文章都有正增益"的错误先验，而这与现实矛盾。保留负标签也是本项目诚实性的一部分。
- *"Δ_f 是因果效应吗？"* → **不是。** 它是同一 f 在加入证据前后的评分差，属于经验监督目标。

### 4.5 在"序列状态建模"处：GRU 与状态前缀

**什么是状态前缀？** 一场比赛在某个采用顺序下的证据快照。例如 s0（未采用）、s1（采用第 1 篇后）、s2（采用第 2 篇后）……项目为每个候选都生成了 s0 转移，并有 3 个有界的前缀顺序（源顺序 / 随机），**深度最多 3**。

**为什么顺序可能重要？** 因为如果先读阵容公告再读转述，与反过来，信息状态不同。

**GRU 做什么？** 它按顺序逐步读取证据向量，用一个 64 维隐状态累积"到目前为止读到了什么"。相比集合表示，它能区分"读了哪些"和"按什么顺序读"。

**当前实验是否证明 GRU 更好？** **没有。** 证据是双向的：

| 指标 | 集合 f | GRU f | 谁更好 |
|---|---:|---:|---|
| f_dev log loss | 0.962041 | **0.958916** | GRU |
| test log loss | **1.022482** | 1.026598 | 集合 |

而且报告说明两者的元数据使用存在差异，所以**不能把差异纯归因于循环结构**。

**顺序敏感性的实测**：在 513 场 / 1,041 篇的完整池上，用源顺序 + 5 个固定随机排列重算，**集合 f 的最终 L1 距离为 0**（置换不变，符合设计）；GRU 在多文场景下最大 L1 均值约 0.001374，**无最高概率类别变化**。

**评委可能追问**：
- *"GRU 是不是必要的？"* → 当前证据不支持。这属于**待验证**。

### 4.6 在"证据准入"处：四项联合约束（旧版机制，新版未接入）

**要解决什么问题？** 一条正文说"某球员正在康复训练"——这句话**既不是"会出场"，也不是"会缺阵"**。如果系统把它当成方向性证据，就会错误地改变概率。

**旧版机制**（`football_agent\directional_evidence.py`）：在保留 `supports / refutes / no_answer` 三态的同时，额外要求**四项同时成立**才允许影响后验：

| 条件 | 要求 |
|---|---|
| **方向标签** | 明确表达利好或利空方向 |
| **相关主体** | 明确指向哪名球员 / 哪支球队 |
| **方向依据** | 说明方向的理由（不是推断） |
| **原文引文** | 提供逐字引文 |

只有状态没有方向的句子（"正在康复""已恢复训练""可供选择"）被记录为 **`unknown + availability_only`**，**不影响后验**。

**三种状态的准确含义**：

| 状态 | 含义 | 对概率的作用 |
|---|---|---|
| `supports` / `refutes` | 四项齐全，方向明确 | 允许进入联合模型 |
| `no_answer` | 正文存在，但不足以支撑该场次的具体断言 | **不改变后验** |
| `unknown + availability_only` | 只有状态、没有方向 | **不改变后验** |

**为什么"证据不足时不更新"比"强行更新"更合理**：因为错误更新的代价是不可逆的。项目在真实历史面板上观察到：5 条观察中只有 1 条通过四项检验，4 条被判 `no_answer`。

**规则式准入 vs 学习式分类器**：四项约束是**规则契约**（人工定义、可审计、可逐条检查），不是学出来的。代价是可能误排有效信息（真实案例：一篇相关正文因未通过主题词表提取而被排除）。

**⚠️ 必须说的三条限制**：
1. **从未做过门控消融**——不知道去掉任一条件后错误更新率会怎么变。
2. 面板**只有 5 条观察**，做 5 臂消融等于每臂 1 条，**没有统计意义**，所以这个消融目前不可行。
3. **不得**把这个机制称为"已验证的完美事实核查系统"。它当前是**待验证的设计贡献**。

**⚠️ 版本提醒**：上述机制属于**旧版在线原型**。**新版全文序列研究使用的是连续增益标签 Δ_f，没有接入这套四项门控。** 不要把两者混成同一个架构。

### 4.7 在"策略评估"处：为什么必须比完整策略

**为什么不能只看 g 的回归误差？**

因为 **g 的误差小 ≠ 策略表现好**。两个原因：
- g 只在"该不该采用"这个决策上有用，回归 MSE 无法反映**决策阈值**的选择质量。
- 最终用户看到的是**预测损失**，不是中间层的误差。

**必须比较的五个策略**（同一比赛集合、同一候选池、同一固定 f、同一预算）：

| 策略 | 含义 |
|---|---|
| **不采用正文** | 只用 s0（校准先验）。基线之下的基线 |
| **固定顺序** | 按冻结的候选顺序逐篇采用，与内容无关 |
| **随机采用** | 随机选篇（每场 10 个 seed 先平均，再按比赛等权） |
| **基于 g 的选择** | 用 g 的分数 + 阈值 + 预算 |
| **原始市场参考** | 市场报价（**对照身份有限制，见下**） |

**为什么必须同池同预算**：否则差异可能来自"候选池不同"或"读得更多"，而不是来自选择策略本身。

**停止条件**：所有候选分数低于阈值时停止；预算耗尽时停止。**当前停止规则没有全局最优性的理论保证。**

**评委可能追问**：
- *"停止规则有理论保证吗？"* → **没有。** 它是在声明范围内的工程停止规则（有限菜单内所有候选非正 / 预算耗尽），不是最优停止。

### 4.8 在"训练与开发"处：监督学习与 Ridge / MLP

**Ridge 回归**：在最小二乘上加 L2 惩罚，目标函数是

```
min_w  ‖Xw − y‖² + α‖w‖²
```

- **为什么加惩罚**：防止在高维小样本上把噪声也学进去（过拟合）。
- **α 的含义**：惩罚强度。本项目所有 Ridge 头统一用 **α = 10.0**。
- **为什么低维结构化特征适合 Ridge**：349 维状态 / 1140 维全文在百量级的比赛上，线性模型方差低、可解释、不易过拟合。
- **标准化纪律**：所有标准化器**只用对应训练折拟合**，测试折只做变换。

**MLP**：多层感知机，本项目为 `1140 → 128 → 64 → 1`，154,369 参数，ReLU 激活 + dropout。

- **为什么全文语义可能需要非线性**：候选与已采用证据的"互补/重复"关系是乘性交互，线性模型需要显式给出交互项（项目已经给了逐元素积），非线性层可以学更复杂的组合。
- **为什么参数量多 ≠ 更强**：本项目有直接证据——**全文 MLP 在 g_fit 上 macro MSE 0.0000067（拟合极好），在 g_dev 上 0.000181，在 test 上 0.000252**，而**恒零基线在 test 上是 0.000212**。也就是说 **MLP 的测试误差大于恒零基线**。这是"训练—评估落差"的直接证据。

**三个 Ridge 必须分清（这是高频混淆点）**：

| 名称 | 在哪里用 | 输入 | 作用 |
|---|---|---|---|
| **state_ridge** | 新版 g 的头之一，且是**开发集选定的策略** | 349 维状态 | 决定**继续/停止**（同状态候选同分） |
| **fulltext_ridge** | 新版 g 的头之一 | 1140 维 | 线性候选排序 |
| 早期诊断 Ridge | C 集（51 场）的 embedding 基准 | 各种文本臂 | 历史诊断，**不是运行模型** |

### 4.9 在"评估指标"处

| 指标 | 定义 | 本项目用在哪 |
|---|---|---|
| **Log Loss** | `−log p(真实结果)`的平均；越低越好 | **主指标**。策略比较、f 评估 |
| **Brier Score** | `Σ (p_i − y_i)²` 的平均；越低越好 | f 评估的辅助指标 |
| **MSE** | 均方误差 | g 的**回归**诊断（比赛等权 macro MSE） |
| **配对 bootstrap** | 以**比赛**为抽样单元重采样，估计差值分布 | 策略对比的不确定性（2,000 次，seed 20261025） |
| **时间切分** | 按时间顺序划分角色 | A 集六个角色 |
| **独立比赛划分** | 以 `physical_match_id` 为分组单位 | 硬约束；前缀不独立计入 |
| **恒零基线** | 预测恒为 0 收益 | g 回归诊断的底线 |
| **市场赔率参考** | football-data.co.uk 的 Avg 报价 | 策略比较的参考行（**时点未验证**） |

**为什么不同任务的 AUC 不可直接比较**：AUC 的含义取决于**标签**。早期项目里有一个广为流传的数字"g 的 AUC 0.544 vs Qwen3 的 AUC 0.918"——但那个标签是**单标注者判读的"标题是否含本场预测相关信息"**，而 g 的输出是 Δ_f 分数。**两者目标不同，不能当作 g 的精度。** 这一点必须主动说明。
