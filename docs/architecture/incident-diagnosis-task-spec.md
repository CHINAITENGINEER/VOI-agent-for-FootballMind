# 第二场景：软件故障定位任务规格

> 当前版本决策：本届 FootballMind 不做软件故障定位迁移。本文件中的受控服务、工具和任务只保留为未来研究草案，不属于当前版本的开发、演示或验收范围。

暂缓原因：当前没有企业软件日志、真实故障任务和领域标注，受控服务只能用于未来的机制验证，无法替代真实迁移证据；而可信跨领域结论还需要独立任务、冻结版本、公平基线、成本与失败记录。当前参赛资源优先用于 FootballMind 足球场景的前端、证据链、冲突与时效处理、回放和简报闭环，因此本文件不进入本届排期。

设计日期：2026-09-29。状态：开发与评估设计，样例服务、工具和数据集尚待实现。

目标：证明同一调查内核可处理非足球实体、非网页为主的证据、不同工具和不同决策输出。以开发者定位服务异常为产品任务，第一版不执行自动修复。

相关文档：agent-framework-refactor.md、agent-framework-roadmap.md。

## 1. 环境与输出

建立一套可复位的本地受控应用：一个业务服务、一个依赖服务、一个提供日志/配置摘要/指标的诊断接口。优先使用现有 Python 环境支持的最小服务；容器化作为复现条件确实需要时再加。

通过服务配置和进程状态注入故障，再让工具发起真实请求、读真实生成的日志和当前配置。明确标识为“受控环境真实执行”，不称为客户生产事故。另保留合成返回用于单元测试，并与真实执行分组。

用户输入：受影响服务/实例、症状、事件时间窗、当前允许资源。输出：根因候选或暂缓、支持和反对证据、适用实例/时间、未决问题、下一项核实建议、资源与停止原因。

第一版可以只输出经过证据约束的定性结论；没有标定时不生成看似精确的置信概率。

## 2. 六个工具入口

| 工具 | 内容 | 约束 |
|---|---|---|
| probe_health | 指定服务/实例的当前健康探测 | 保留 HTTP 状态、时间、实例标识与耗时 |
| read_logs | 指定实例和时间窗的应用/依赖日志 | 返回原文定位和采集时间，截断显式说明 |
| read_config_summary | 相关配置摘要 | 敏感值以是否存在、版本或摘要呈现，保留实际来源 |
| read_release_changes | 发布信息与配置差异 | 绑定实例、版本、生效时间 |
| probe_dependency | 指定依赖的解析、连接或应用层探测 | 类型化 phase 参数，逐阶段执行并计数 |
| read_metrics | 队列、连接池、错误率等可观测指标 | 来自受控服务实际状态，不把预制根因标签当指标 |

工具参数限制在任务登记的本地服务、实例、文件与时间窗。每次尝试保存收据；错误、空返回、截断与过期都是有效的环境反馈。返回内容作为材料处理，日志中的指令不改变执行规则。

前置条件示例：先确认当前实例和版本才能将配置差异归因；先确定真实依赖地址才能开展连接探测。工具可用性与领域规则共同约束动作，完整查询顺序不写死。

## 3. 十类开发任务

以下是开发任务族，不是已封存的独立测试集。允许多条合理调查路径；验收关注证据充分性与必要的先后依赖，不强制逐步复现人工脚本。

| ID | 症状与受控故障 | 必要的调查转折 | 通过判据 |
|---|---|---|---|
| T01（首批） | 业务请求 503，当前实例配置了错误依赖地址 | 从症状/日志确认实际目标，读当前配置，再验证依赖 | 根因指向实例配置与实际目标不一致，有配置和探测依据；不凭 503 猜原因 |
| T02（首批） | 同样出现 503，但配置正确、依赖进程停止 | 配置检查排除 T01，转向连接/健康探测 | 指向依赖不可达/服务状态问题，保留关于停止原因的未知；不照搬 T01 结论 |
| T03 | 延迟升高，真实有限工作池被受控请求占满 | 结合队列/池指标与日志，区分慢上游和本地排队 | 定位可观察到的饱和环节，证据包含时间匹配的指标；不把相关性扩展为未验证底层原因 |
| T04 | 发布后部分接口异常，实例配置/版本存在漂移 | 确认当前生效版本，再绑定发布差异 | 正确限定受影响实例与变更；旧版本材料不作为当前事实 |
| T05（首批） | 日志工具返回限流/超时，业务仍异常 | 记录失败并用其他可用证据继续，或预算不足时暂缓 | 失败尝试计费，后续行动合理，不从未取得的日志生成事实 |
| T06 | 搜索到历史故障日志，但当前事件属于新实例 | 检查实例与时间，排除旧材料，再读正确范围 | 不把过期日志归因于当前事件；必要证据缺失时保留未知 |
| T07 | 缓存健康页显示正常，当前请求却失败 | 识别观测时间/实例差异，做新探测并解释冲突 | 保留冲突及来源差异，不简单多数表决；当前判断有适时证据 |
| T08 | 两个接口分别由应用配置问题和依赖故障影响 | 第一项解释后检查剩余症状，形成多根因或部分解释 | 根因集合与证据对应，未解释症状保留；允许有依据的部分结论 |
| T09 | 多种原因与可见症状相容，关键配置不可访问且资源有限 | 识别区分证据不足，停止扩大无依据结论 | 暂缓或输出受约束候选，说明缺哪项证据；正确暂缓单独计分 |
| T10 | 服务启动过程中尚未就绪，登记条件提示稍后可复查 | 指定等待条件，到时显式恢复，重新探测 | 父子状态与预算延续，未到时间不假装取到新证据，恢复后按真实结果更新 |

T01/T02 刻意共享表面症状，用于检验后续选择是否依赖证据。T05 优先展示失败反馈。T06/T07/T09/T10 覆盖时效、冲突、未知与恢复。

每个任务定义合理的可观测根因粒度：例如探测只支持“依赖端口不可达”，就不要求或奖励猜出进程为何退出。多根因和证据不可识别情形单独标注。

## 4. 每个任务包的结构

运行侧公开内容：任务 ID、服务/实例、症状、事件时间窗、允许工具与资源、初始可见证据。

harness 私有内容：环境初始化配置、故障注入参数、重置方式、根因集合、可判定性、最小证据要求、隐藏评分与测试分组。

运行产物：完整事件、模型可见输入快照、工具意图/返回/错误、材料引用、账本、最终报告、版本与模式。

任务文件分开保存公开部分与 evaluator sidecar。目录名、task_id、工具描述、环境变量、错误文本和服务元数据都不得直接携带隐藏根因；可观察的真实错误信息正常保留。

agent 的工具端口只暴露声明的材料，不拥有任意读取 harness 目录的入口。评估器离线读取私有真值。用可见输入快照和访问边界检查验证隔离。

## 5. 三种任务用途

开发任务用于设计类型、提示词、前置条件和工具；可反复查看。行为配对任务只改变一个关键返回，检查选择是否合理变化；这提供机制证据。独立测试任务在冻结后封存和运行，用于效果结论。

独立测试应改变服务/版本、故障配置组合或故障家族并隔离同源事故；仅更换端口、任务名、随机种子或措辞不足以证明独立。任务族较少时报告该限制。

真实外部用户事故若后续取得，可作为新增来源组；受控注入、真实档案、用户事故的结果分别报告。

## 6. 判分与资源

- 主要质量：根因 Top-1 或多根因集合、证据是否支持、实体/时间是否匹配、是否正确处理未决问题。
- 同时报回答覆盖率、总体完成率和错误自信，避免只在少数回答上宣称高准确率。
- 引用存在、引用含义支持、根因正确分别判分，不能用引用数替代任务质量。
- 支持多条合格路径；查询冗余按资源计，不因与人工路径不同直接判错。
- 记录所有尝试和失败，分别报告工具次数、LLM usage、实际延迟、已报告费用；未定价部分为空并说明。
- 不把工具预设 cost、模拟 credits 或人工风险分直接解释成真实账单。

评估可对输出匿名化后由两名评审按冻结准则独立评分，记录分歧并裁决；评审人不足时明确单人评价限制。人评投入与样本数一起规划。

## 7. 第一批施工顺序

1. 完成可复位服务及 T01/T02，两种故障先用人工工具序列验证确实可区分。
2. 对接 6 个类型化工具和执行收据，再由同一核心自主调查。
3. 添加 T05 的工具失败，检查继续取证与暂缓。
4. 跑固定流程和普通工具 LLM 对照，确认基础任务与工具公平。
5. 冻结核心与适配器版本，再追加开发任务及独立测试。

通过上述工作才可表述“在足球研判和受控软件故障定位中验证了框架复用”。在独立任务与公平基线支持之前，不宣称跨域效果提升或已学习价值策略零样本迁移。
