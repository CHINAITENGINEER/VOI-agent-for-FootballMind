# 自主取证框架：实施路线与验收

设计日期：2026-09-29。状态：计划；日期和数量是工作安排，不是已完成结果或获奖承诺。

当前产品方向修订：本届版本以单领域 FootballMind 赛前赛事情报与证据研判工作台为交付目标，不把第二领域迁移作为硬交付。产品包装、前端和单领域验收以 [FootballMind 项目升级与产品包装规范](../product/footballmind-product-upgrade-spec.md) 为准；本文件中的第二领域路线保留为未来有真实数据和合作资源时的可选方案。

下文 V0/V1 的内容是跨领域迁移的历史设计草案，不是当前参赛版本的排期或验收清单。

当前执行结论：本届不实施 V0/V1 的迁移路线，不创建第二领域适配器，不运行跨领域对照实验。

暂缓原因：项目当前缺少真实第二领域数据、企业日志、稳定工具接口和独立评价样本；迁移需要冻结核心、建设领域适配、准备公平基线并完成失败分析，远超“接一个插件”的工作量。当前更重要的是把 FootballMind 的单领域产品、前端工作台、证据链和可复盘演示做完整。没有这些证据时，第二领域只能形成受控展示，无法支撑通用迁移结论，还会分散参赛版本的交付重点。

2026-09-29 准入修订：扩大改造以前先执行 `migration-entry-standard.md` 的 A/B 门。下述十天日历仅为尚未核定人手与工时的安排草案，不作为交付承诺；准入证据和学校实际截止优先。

配套架构：agent-framework-refactor.md。第二领域开发任务：incident-diagnosis-task-spec.md。

## 1. 两个版本与排期前提

V0 为参赛可演示版本：保留足球应用，接入统一协议，在受控故障服务上跑通少量真正执行的诊断任务，并有明确来源标识、成本和回放。V1 为可论证迁移的版本：冻结核心、完善第二领域和独立评估，再给出效果结论。

官方 2026 年通知写明校赛于 10 月 10 日前完成，省赛/区域赛报名于 10 月 15 日 20:00 截止。学校和赛区可能有更早内部日期。官方来源：https://www.aicomp.cn/notice/notice-1/3674.html 。2026-09-29 已核对通知正文。

以下按 9 月 29 日开始、已有可用 Python 环境和模型接入来倒排；人手和每天投入尚未确认，因此是建议日历，验收门优先于日历。若本校截止更早，压缩范围而不是压缩真实性。

## 3. 工作包的施工细目

### P0：建立可恢复基线

- 根目录当前不是 Git 仓库；先建立基线快照或版本库，记录源文件、依赖、模型/提示词配置和数据清单的哈希。
- 选正常取证、来源冲突、工具失败/预算不足三条足球轨迹；真实、历史回放和合成各自标识。
- 记录最新上下文循环已有累计声明成本、执行回调和决策回调；不把它们当作待补空白。
- 给目标用户写一个明确任务：何时使用、输入是什么、最终拿到什么、有何证据要求。

### P1：先做一个兼容纵切面

- 新增核心协议，先用 football adapter 桥接现有 InquiryWorkflow。
- 从纯数据类型、PublicView、前置条件、证据引用和报告 schema 开始抽取；每抽一块跑该块回归。
- 核对 state_query_contract 中 evaluator 标注与真实观察状态的区别，避免把隐藏状态直接迁成 agent memory。
- 检查调用链依赖：最终冻结核心不得直接或传递依赖足球模块。
- 保留旧研究协议与有限模型假设；将新入口接通后才逐步迁移旧 CLI/demo。

### P2：统一执行与第二域接入

- 复用已有累计预算机制，补齐多资源预留、执行收据、未知费用和父子运行账本。
- 将公共可行性门控与有限模型价值选择/开放探索分离，避免通过伪造 VoI 执行新领域工具。
- 工具超时、失败、晚到、重复、已调用未确认都进入事件日志。
- 故障场景通过受控真实服务产生日志和探测返回；故障配置与真值只对 harness/evaluator 可见。
- 先完成 T01/T02/T05，再扩展其他类型；每类至少有改变关键证据后调查路径相应变化的配对任务。

### P3/P4：产品与参赛材料

- 工作台首屏围绕任务、证据、下一步、决策和成本；减少默认暴露的工程配置。
- 提供正常成功、冲突改判、失败后暂缓三类可重复演示。
- 在线演示出故障时可切换已归档回放，页面明确模式。
- 用户试用建议邀请 3–5 名目标用户，记录任务完成时间、可用性问题和原始反馈；不得把试用目标写成已验证收益。
- 提交材料包含：真实问题、架构、三项创新、对照实验、应用验证、局限和演示入口。

## 4. V1：冻结核心后的验证与完善

建议在 V0 冻结后安排 2–4 周，按当地赛程和实际工时裁剪：

| 工作 | 产物 | 判断标准 |
|---|---|---|
| 补齐 10 类开发任务 | 每类任务定义、服务状态、工具和判分规则 | 覆盖缺失/冲突/时效/依赖/失败/预算 |
| 核心接口稳定与依赖清理 | 同一核心工件、两个 adapter、兼容回归 | 接入差异可审计，足球回归通过 |
| 独立留出任务 | 按实体/事件/故障家族隔离的测试清单 | 不与开发/调参任务共享同一事件或等价模板 |
| 配对实验与消融 | 原始轨迹、指标脚本、表格、失败分析 | 参数冻结，所有运行计入，报告不确定性 |
| 用户试用与材料更新 | 有日期的任务记录与反馈 | 用户实际完成任务，收益按观察结果表述 |

首版不以第三领域作为里程碑；只有两域稳定、对照完成、时间允许时，才考虑增加规则核验等第三领域。

## 5. 评估设计

### 5.1 数据隔离与冻结

- 开发任务：用 10 类故障定义和既有足球任务调试 schema、提示词、阈值、工具。
- 测试任务：冻结后新建或预先封存，开发阶段不可查看测试标签和中间工具返回；新随机种子不自动代表独立任务。
- 足球按比赛/实体/时间拆分，同一比赛不同 cutoff 不跨开发与测试；历史重建与实际前瞻评估分开。
- 故障按事件与配置/故障家族拆分，同一事故的多条日志、多条运行和扰动版本不当作独立样本。
- 核心、adapter、模型配置、提示词、工具、时间策略和样本清单共同冻结。冻结后变更产生新实验版本。

### 5.2 基线和公平性

| 组别 | 定义 | 共享条件 |
|---|---|---|
| B0 固定调查流程 | 预先写定工具顺序与停止规则 | 相同任务、来源、工具及资源上限；需要总结时使用相同模型 |
| B1 普通工具型 LLM | 模型可以调用同一工具集，仅使用基本任务提示与硬执行限额 | 与框架同模型、工具、数据可见性、超时和资源上限 |
| B2 本框架 | 明确问题/证据状态、前置条件、重规划、停止说明 | 同一底层执行器、故障环境、缓存和资源核算口径 |

基础执行正确性、时间截断和标签隔离适用于所有组，不作为让基线故意出错的优势。先保证 B1 是合理可用的实现，再比较显式证据机制的增益。所有方法共用执行器，B1 不暗中获得额外查询预算。

实时网页不可重放时，同一任务顺序执行会受环境变化影响：采用同一时间窗并保留快照，或用动态封存环境提供按需结果；明确归类为在线或回放，不混报。缓存冷/热条件保持一致，不能把前组的采集成本转移给后组。

先在小型开发预试验估算每次运行资源，再决定最终样本量。30–50 个独立任务/域可作为初始规划区间，不是统计充分性保证；依预期差异、方差、相关性和资源修订。

主实验先固定一个业务认可的资源档位。另在预先选择的子集跑多预算/多随机重复；随机性显著的主结果应增加重复。LLM 内部随机性不可固定时照实记录。任务级配对比较，并按比赛/事故聚类估计区间，重复运行不扩充独立样本数。

### 5.3 指标

| 维度 | 统一报告 | 领域专用指标 |
|---|---|---|
| 任务质量 | 成功率、未完成率、正确暂缓与错误自信、带结论的覆盖率 | 足球：事实支持、范围/时间正确性、简报可用性；故障：根因 Top-1/候选集合、证据支持 |
| 证据 | 需要来源的断言中具有有效引用的比例、引用含义支持、冲突遗漏 | 由领域规则和盲评确定 |
| 成本 | HTTP 尝试、LLM 调用、tokens、实际耗时、可报告货币费用 | 未定价项单列；仿真成本不称在线实际花费 |
| 可靠性 | 超时后行为、预算门控、晚到隔离、恢复后重复调用、回放一致性 | 不同模式分组 |
| 迁移 | 接入工时、修改核心文件/行、领域代码与依赖、开发/标定样本 | 原冻结核心与修改后核心分版本 |

选择性准确率必须与回答覆盖率、整体完成率一起看，防止通过一律暂缓得到虚高质量。多根因任务使用集合判分，不强制只有一个根因。

Brier/log loss 只用于真正输出并可评分的概率预测。足球文本简报与故障根因准确率不混成一个均值；各域分别给出质量—成本关系。

如追求“质量不下降而成本降低”，在看测试结果前约定业务可接受的质量差异范围。测试未支持收益时报告负结果和失败类别，避免只选表现好的预算点。

### 5.4 消融

优先比较去掉显式前置依赖、去掉冲突状态、去掉有界停止选择、去掉反馈重规划。公共时间/预算执行约束始终保留。价值模型消融仅在确有校准支持的子集使用，不把开放探索冒称学习型 VoI。

## 6. 硬验收门

| Gate | 通过条件 | 未通过时处理 |
|---|---|---|
| G0 基线 | 选定历史轨迹可读取、来源分类准确、版本可恢复 | 暂缓提取共享模块 |
| G1 兼容 | 关键足球任务结果与事件语义保持，旧入口和旧档案可用 | 回到兼容桥修正 |
| G2 执行 | 已知成本正确累计，未知费用显式；失败/重试有收据，晚到证据隔离 | 暂缓真实效果比较 |
| G3 迁移 | 双领域同一核心工件；私有标签不进入 Planner/公开视图 | 只报告适配进度，修正隔离 |
| G4 行为 | 配对环境返回导致合理分支；证据不足时可暂缓 | 不声称自主适应已验证 |
| G5 效果 | 冻结协议、公平基线、独立样本、完整失败记录 | 只报告探索性结果 |
| G6 交付 | 新环境按 README 启动、来源标识完整、三类演示可重复 | 先修发布流程 |

这些是拟定的验收标准，不是本次已经跑过的测试。实施时围绕真实错误风险设计检查，避免只测试字段恰好长成实现代码的样子。

## 7. 最终产物与宣传边界

代码：核心协议/运行时、两个 adapter、工作台、安装入口。证据：原始材料、工具收据、回放、版本清单、独立评估与用户反馈。材料：架构图、3 分钟演示、对照结果、失败案例、使用说明。

三项主张分别对应证据：按问题选择证据 → 分支与消融；预算内重规划/停止 → 执行账本与成本—质量比较；可迁移架构 → 核心冻结后的第二领域接入记录。

本次工作仅新增设计文档；不据此声称泛化性能提升、已完成第二场景、已完成在线费用结算或能够保证获奖。
