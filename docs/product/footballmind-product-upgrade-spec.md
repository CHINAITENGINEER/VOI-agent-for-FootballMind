# FootballMind 项目升级与产品包装规范

文档版本：v1.1  
制定日期：2026-09-29  
适用范围：当前足球赛前信息研判项目  
实施状态：设计稿，尚未代表全部功能已经交付

本次修订：补充“本届不做跨领域迁移”的决策依据，并将迁移相关内容明确为未来研究储备。

## 当前版本决策

**本届项目明确不做跨领域迁移。** 不接入软件故障、工业设备、网络安全、校园设施或其他第二领域，不以第二领域适配、跨领域实验或通用迁移作为本届交付、创新点、演示内容或验收条件。

本届只把 FootballMind 做成一个完整的足球赛前赛事情报与证据研判产品。现有通用状态、查询、预算、审计和回放能力仅服务于足球场景；未来如果取得真实合作数据，再另立版本讨论迁移。任何旧文档中的第二领域路线均属于未来备选设计，以本节和本产品规范为准。

### 为什么本届不做跨领域迁移

这是基于证据条件、交付资源和参赛表达的范围决策，不代表否定内部模块化设计。

1. **目前缺少真实的第二领域数据。** 项目手头没有企业软件日志、稳定的第二领域工具接口、真实任务分布和领域专家标注。现在接入第二领域只能主要依赖合成或受控样例；这可以展示接口是否跑通，却不足以支撑迁移后的业务价值、鲁棒性和效果结论。
2. **可信迁移不是增加一个适配器。** 一次可审查的迁移至少需要冻结核心协议和版本，定义第二领域的实体、证据、工具与评价规则，准备未参与开发的独立任务，与固定流程或工具型基线做公平对照，并完整记录成本、失败和核心改动。当前人力和比赛时间优先完成这些工作，会直接挤压主场景的产品化质量。
3. **FootballMind 的主场景还需要做深。** 当前最有价值的工作是补齐前端任务流程、关键未知展示、来源冲突处理、时效截止、证据链、事件回放和可导出简报。如果同时铺开第二领域，最终容易形成两个都不完整的演示，反而削弱项目的技术主线。
4. **跨领域主张的证据成本高。** 即使做出一个受控的第二领域案例，也只能说明声明任务和资源条件下的接入情况，不能直接推出“适用于任意行业”或“零样本迁移”。在独立样本、基线和失败分析尚未具备时，把通用迁移写成创新结论会超过现有证据，影响项目可信度。
5. **单领域闭环更符合本届交付优先级。** 在相同资源下，先把一个明确用户、明确任务、明确输入输出和明确审计证据的足球场景做成可运行、可复盘、可重复演示的产品，更有利于评委判断真实问题、技术机制和应用价值。

因此，本届保留通用接口、状态协议、预算、审计和回放等内部扩展基础，但不投入第二领域开发，不把迁移效果写入产品承诺。未来只有在获得真实数据、合作任务和独立评估条件后，才另立版本重新评估迁移。

## 1. 文档目的

本文件将 FootballMind 从研究型足球信息获取项目，收敛为一个可以演示、试用、评估和提交的软件产品。升级重点是产品定位、用户流程、证据展示、事件回放和前端工作台，不启动跨领域迁移，也不要求重写现有后端。

本版本的产品主张只覆盖足球赛前信息研判。通用状态、查询、预算和审计能力可以继续作为内部设计基础，但不对外宣称已经验证了跨行业迁移。

本文件不承诺预测命中率、投注收益、企业部署或竞赛名次。所有“已完成”与“待验证”必须在参赛材料中分开。

## 2. 产品定位

### 2.1 产品名称

产品名称：**FootballMind：赛前赛事情报与证据研判工作台**

技术副标题：**面向动态多源信息环境的自主取证与可审计研判系统**

英文名称可保留 FootballMind；中文产品名不使用“彩票”“投注”“下注”“博彩”“套利”等词。

### 2.2 目标用户

首个目标用户只选择一类：体育内容编辑或赛事研究人员。其具体任务是，在比赛开始前的限定时间内，快速核验阵容、伤停、排名、赛制和近期状态，形成一份有来源、时间和不确定性说明的赛前简报。

球迷、俱乐部、数据平台和普通用户可以作为后续用户画像，不写入首版主要承诺。当前项目不能同时为不同用户设计完全不同的价值标准。

### 2.3 用户问题

> 赛前资料很多，但来源可能冲突、信息可能已经过期、关键状态可能尚未确认。编辑需要知道当前缺什么、下一步查什么、哪些内容可以写进简报，以及哪些内容必须保留为未决。

### 2.4 产品承诺

> FootballMind 根据任务、截止时间和当前证据状态，选择必要的核验路径，处理来源冲突和信息失效，生成带证据链的赛前赛事研判简报，并保留可回放的调查过程。

产品承诺是减少无效检索和未经证实的信息引用，不承诺改变比赛结果，也不提供下注建议。

### 2.5 AIC 参赛方向

首选 AI+软件创新方向。作品以可运行的 Web/本地工作台、完整核心流程和可复查运行记录作为软件产品交付。AI+场景创新可以作为备用方向，但如果选择该方向，需要额外准备用户需求、试用记录和场景效果材料。

## 3. 当前项目基线

当前项目已经包含不少可复用的执行能力：足球数据与档案适配器、时间截止、证据状态、查询和预算约束、失败与等待处理、运行事件、原始材料引用、报告和回放。

现有 demo/static/index.html、app.js 和 style.css 已经提供一个工程型回放界面。它的优点是能显示模型、截止时间、工具调用、概率、证据、预算和事件；它的问题是首屏以“工具工作流/事件回放”和“胜平负概率”为中心，工程配置多，用户任务、关键未知、下一步理由和最终简报不够突出。

因此本次升级的原则是：保留当前 HTTP API、运行存储和事件回放能力，先改善产品信息架构和显示层；只有现有数据结构确实没有所需信息时，才增加小型摘要接口。首版不迁移到 React，也不重写 Python 服务。

## 4. 产品范围

### 4.1 首版必须完成

1. 创建一个赛前研判任务，选择比赛、调查截止时间和资源上限。
2. 展示当前已知、未知、冲突和过期风险。
3. 显示系统下一步准备查询什么、针对哪个未知、为什么现在查询。
4. 执行下一步或运行至停止，取得真实档案、实时返回或明确标记的测试返回。
5. 每次返回后重新展示状态变化、证据变化和下一步动作。
6. 生成赛前研判简报，包含结论、证据、来源时间、适用范围、未决问题和资源摘要。
7. 支持事件时间线、节点回放、原始材料引用和完整 JSON 导出。
8. 清楚区分在线运行、历史档案回放、受控测试和合成数据。

### 4.2 首版不做

- 不做跨行业插件市场和第二领域适配器。
- 不把概率模型和赔率模块放在主产品流程中心。
- 不提供下注、投注、收益或套利建议。
- 不承诺企业生产环境部署。
- 不把研究性概率结果与文本证据自动合并成未经验证的最终概率。
- 不引入复杂账号、团队协作、云端部署和多智能体编排。
- 不为了视觉效果重写已经能工作的执行、存储和回放后端。

## 5. 目标用户流程

### 5.1 进入产品

用户看到产品名称、目标任务和三个模式入口：

- 开始一次赛前研判：创建新任务。
- 打开历史运行：查看已有运行和报告。
- 观看示例：进入预先准备的正常、冲突、失败三个案例。

首页不直接展示胜平负概率。首页先回答“这个系统解决什么问题”和“我可以查看什么结果”。

### 5.2 创建任务

创建页面只保留用户需要理解的字段：

- 比赛；
- 研判截止时间；
- 希望回答的问题；
- 可用信息模式；
- 查询资源上限。

模型版本、数据 reader、档案路径、工具版本、配置哈希和调试参数放入“技术详情”，不放在首屏主流程。

### 5.3 研判工作区

工作区按“任务—状态—下一步—证据—时间线—报告”组织：

1. 顶部显示比赛、截止时间、当前模式和运行状态。
2. 第一张卡显示当前任务与一句话状态。
3. 第二张卡显示关键未知和冲突。
4. 第三张卡显示下一步动作、目标未知、选择理由和预计资源。
5. 中部显示当时可见证据和证据时间。
6. 下部显示事件时间线和选中事件详情。
7. 右侧或底部提供生成报告、等待、暂缓和查看技术详情。

### 5.4 结束与报告

报告至少包含：

- 研判结论；
- 已确认事实；
- 尚未确认的关键问题；
- 冲突来源及其处理方式；
- 证据来源、发布时间和观察时间；
- 结论适用的比赛与截止范围；
- 查询次数、模型调用、耗时和已知费用；
- 停止、等待或暂缓原因；
- 研究性模型结果（如果存在）及其单独标识。

## 7. 前端改造建议

### 7.1 首屏改造

现有首屏的“工具工作流 / 事件回放”改为：

- 品牌：FootballMind
- 副标题：赛前赛事情报与证据研判工作台
- 主标题：在开赛前，知道哪些信息已经确认。
- 说明文字：系统根据截止时间和当前证据状态选择核验路径，生成带来源和不确定性说明的赛前简报。
- 模式标签：历史回放、现场运行、受控测试、合成演示。

首屏主按钮使用“开始赛前研判”，不要使用“初始化运行”。“初始化运行”保留在技术详情或开发模式。

### 7.2 研判状态卡

将当前的“胜平负概率”卡改为首屏主卡：

~~~
当前研判状态
已确认  4 项       待核实  2 项       冲突  1 项

当前结论
首发阵容尚未由官方来源确认，暂不把媒体报道作为确定事实。

下一步建议
核验官方首发信息
目标：starting_lineup
理由：该信息可能改变赛前简报中的阵容判断
预计资源：1 次来源请求
~~~

概率图可以保留在“模型参考”卡中，默认折叠或放在报告的附加部分。

### 7.3 证据卡

每条证据卡至少显示：

- 证据标题；
- 证据类型；
- 来源；
- 发布时间；
- 系统观察时间；
- 当前截止时间；
- 是否在截止前可用；
- 适用对象；
- 与当前未知的关系；
- 状态：支持、反对、上下文、过期、冲突或未确认；
- 原文引用或原始材料入口。

当前界面中的“来源 + 版本”信息可以保留，但需要补充“为什么它出现在这里”和“它支持哪个判断”。

### 7.4 下一步行动卡

下一步行动必须成为界面最明显的操作区域。建议显示：

- 查询名称；
- 目标未知；
- 可能改变什么判断；
- 预计调用和费用；
- 选择理由；
- 执行按钮；
- 暂缓按钮；
- 查看候选动作按钮。

不要只显示“执行下一步”。用户需要理解系统为什么执行这一项。

### 7.5 事件时间线

现有时间线已经是项目的优势，应从调试日志改成用户可以理解的调查过程：

- 发现未知；
- 提出核验问题；
- 选择来源；
- 取得证据；
- 发现冲突；
- 更新判断；
- 重新规划；
- 生成报告；
- 等待；
- 暂缓。

工程事件名、请求 nonce、哈希和原始 JSON 放入“查看技术详情”。时间线主文本使用用户语言。

### 7.6 预算显示

默认显示三项：已用查询、剩余查询、已用时间。费用单位必须明确写成“工具计费单位”或“费用未知”，不能让用户误解为人民币实际账单。

最大工具调用、最大来源请求、模型配置和运行超时等设置放入高级选项。

### 7.7 示例案例

首页准备三个一键案例：

1. 正常核验：查询一项缺失信息后形成简报。
2. 来源冲突：两个来源内容不一致，系统继续核验并保留冲突。
3. 证据不足：来源超时或晚于截止，系统暂缓并说明缺口。

每个案例都应在入口处标明“历史回放”“受控测试”或“合成演示”。

### 7.8 技术栈建议

首版继续使用当前原生 HTML、CSS 和 JavaScript。现有 app.js 已经有 API 调用、事件回放、证据渲染、预算渲染和报告下载能力，先做信息架构和组件样式调整，不因为“产品化”而引入 React、构建链或新的状态管理框架。

建议先把页面拆成以下前端函数或组件概念：

- TaskHeader：任务、截止时间、模式和状态；
- DecisionSummary：当前研判与关键未知；
- NextActionCard：下一步动作和理由；
- EvidenceCard：来源、时间、适用性和状态；
- EventTimeline：事件列表和回放；
- ResourceSummary：预算、耗时和费用；
- ReportPreview：报告摘要和导出；
- TechnicalDetails：原始 JSON、版本和哈希。

这只是前端组织方式，不要求马上引入框架。

## 8. 后端和 API 适配

当前 /api/config、/api/matches、/api/runs、/api/runs/{run_id}/action、/api/runs/{run_id}/report 和 blob 读取接口可以继续使用。现有 API 已能提供运行、事件、证据、概率、预算和配置，先不要大规模更换接口。

为了支撑产品工作区，建议在服务端增加一个面向显示层的派生摘要，不改变底层审计记录：

~~~
{
  "task": {
    "title": "赛前阵容与伤停核验",
    "subject": "主队 vs 客队",
    "cutoff": "2026-09-20T11:10:00Z",
    "mode": "archive_replay"
  },
  "decision": {
    "status": "needs_evidence",
    "summary": "首发阵容尚未由官方来源确认",
    "unknowns": ["starting_lineup"],
    "conflicts": 1,
    "next_action": "核验官方首发信息",
    "reason": "该信息可能改变当前研判"
  },
  "resources": {
    "queries_used": 1,
    "queries_remaining": 2,
    "elapsed_seconds": 4.2,
    "known_cost": null,
    "cost_status": "unknown"
  },
  "provenance": "archive_replay"
}
~~~

这个摘要是显示投影，不应覆盖原始运行记录。回放到不同事件时，摘要必须从所选事件快照重新计算，不能直接使用最终结果。

可选新增接口：

- GET /api/product：产品名称、版本、模式说明和产品边界；
- GET /api/examples：三个演示案例的标题、类型和运行 ID；
- GET /api/runs/{run_id}/summary：从运行快照生成当前工作区摘要。

如果短期不想新增接口，前端可以先从现有运行记录派生摘要；但最终报告、模式标签和下一步动作最好由后端返回经过校验的字段。

## 9. 数据和产品边界

所有运行结果必须显示来源类型：

| 标签 | 含义 | 展示方式 |
|---|---|---|
| 在线运行 | 在当前运行中调用配置好的来源或服务 | 在线运行 |
| 历史回放 | 读取此前保存的材料，不发起新的外部请求 | 历史回放 · 零联网 |
| 受控测试 | 在本地测试服务或固定故障环境中运行 | 受控测试 |
| 合成演示 | 预置返回，仅验证流程 | 合成演示 |

前端不得用统一的“真实”标签覆盖这四种情况。已有含合成上下文的轨迹，必须继续在界面上明确标注。

预测概率、赔率和市场信号如果保留，统一放在“模型参考”区域，并显示模型版本、输入版本、截止时间和适用限制。它们不应成为产品首页标题或最终行动按钮。

## 10. 评估与验收

### 10.1 产品任务验收

建议准备 15 个足球赛前任务：

- 5 个信息充分任务；
- 5 个存在冲突、过期或来源质量问题的任务；
- 5 个在资源或截止条件下确实不能确定的任务。

每个任务提前定义：问题、允许证据、正确范围、截止时间、允许的部分结论、合格的暂缓条件和硬错误。

### 10.2 建议指标

- 关键断言是否有实际来源支持；
- 引用内容是否真的支持断言；
- 比赛、球队、球员和时间是否匹配；
- 是否使用了截止时间之后的信息；
- 是否识别并保留冲突；
- 是否在证据不足时暂缓；
- 查询次数、工具调用、耗时和已知费用；
- 运行是否能够完整回放；
- 目标用户完成任务所需时间和反馈。

建议把“事实支持率”“时间/作用域正确率”“正确暂缓率”和“查询资源消耗”作为主指标，不把胜平负概率作为唯一产品指标。

### 10.3 前端验收

- 新用户在 30 秒内能理解产品用途和目标用户；
- 用户能区分在线、回放、受控测试和合成演示；
- 用户能在一个页面看到当前未知和下一步理由；
- 用户能查看某条结论对应的来源和时间；
- 用户能在回放中看不到未来事件结果；
- 用户能生成并下载一份结构清晰的赛前简报；
- 移动宽度下不出现横向滚动，核心操作仍可使用；
- 所有失败、等待和暂缓状态都有中文解释。

## 11. 实施顺序

### P0：产品包装与文案

- 确定产品名称、副标题、目标用户和主任务；
- 删除首屏彩票、下注和收益导向文案；
- 将 demo/static/index.html 的标题、主标题、说明和按钮改成赛前研判语言；
- 将模型概率调整为次级模块；
- 增加模式标签和产品边界说明。

验收：不运行后端，仅打开页面，评审能够说出产品给谁用、解决什么问题、输出什么结果。

### P1：工作区信息架构

- 增加当前研判摘要、关键未知、冲突和下一步行动卡；
- 重排证据、时间线、预算和技术详情；
- 把现有工程事件名转换为用户可读标签；
- 保留原始 JSON 和 blob 入口。

验收：用一个已有运行记录打开页面，用户不看代码也能复述系统做了什么。

### P2：报告和示例

- 准备正常、冲突、证据不足三个可重复案例；
- 增加报告预览和导出；
- 在报告中加入来源类型、截止时间、未决问题和停止原因；
- 记录案例准备方式和数据边界。

验收：三类案例可以按同一操作流程运行或回放，页面不把合成数据称为在线真实结果。

### P3：小规模用户试用

- 找 3～5 名体育内容编辑、赛事研究人员或有实际赛前分析需求的用户；
- 给每人同样的 2～3 个任务；
- 记录完成时间、发现的误导点、看不懂的字段、是否愿意使用报告；
- 根据反馈做一次界面冻结。

验收：用户反馈、任务记录和版本号可追溯；不把用户主观喜欢直接写成效果提升。

## 12. 参赛材料包装

### 12.1 一句话介绍

> FootballMind 是面向体育内容编辑和赛事研究人员的赛前赛事情报与证据研判工作台，帮助用户在信息不完整、来源冲突和时间受限的情况下，选择必要的核验路径，形成带来源和不确定性说明的赛前简报。

### 12.2 三项创新

1. **面向关键未知的主动取证**：根据当前状态选择可能改变研判的查询，而不是固定搜索全部资料。
2. **带截止时间和作用域的证据管理**：区分来源发布时间、观察时间、可用时间和适用对象，避免将过期或错位信息写入结论。
3. **可审计的动态研判**：证据返回后重新规划，遇到冲突、失败或预算不足时可以继续、等待或暂缓，完整保留事件和资源记录。

### 12.3 三分钟演示脚本

1. 选择一场比赛和赛前截止时间，输入“核验阵容、伤停和近期状态”。
2. 系统列出已知信息、关键未知和首个核验动作。
3. 执行一次查询，展示证据来源、发布时间和适用范围。
4. 引入来源冲突，展示系统不直接合并矛盾内容，而是选择继续核验。
5. 让一个来源超时或晚于截止时间，展示失败记录、预算变化和暂缓结论。
6. 打开赛前简报，展示证据引用、未决问题和停止原因。
7. 回放到中间节点，证明系统当时没有看到后续事件。

## 13. 宣传边界

可以说：

- 面向赛前复杂信息环境；
- 自主选择证据获取路径；
- 支持来源冲突和时效检查；
- 形成可追溯的赛前研判简报；
- 支持历史回放、受控测试和运行审计。

当前不应说：

- 提高彩票中奖率；
- 提供下注建议；
- 保证比赛预测准确；
- 已经验证企业级通用迁移；
- 已在真实生产环境落地；
- 通过模型概率直接指导用户决策获利。
