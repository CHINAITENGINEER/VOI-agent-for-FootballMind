## 4. 目标数据流与模块边界

数据流：

外部来源 → Collector → 原始观测档案 → Normalization → 实体解析与质量校验 → PostgreSQL 规范化历史层 → 按时点生成特征 → 离线 Feature Store。

建议沿用现有包结构，按需新增：

```text
collectors/          统一采集协议、spftll 适配器及真实新增来源
normalization/       来源字段转换、比赛/球队/赔率/事件归一化
models/              有类型的数据契约
storage/             PostgreSQL repository、原始档案、迁移
identity/            实体来源映射、别名、待确认匹配
quality/             规则、质量问题、隔离与处理记录
features/            时点查询、特征计算、版本化离线输出
scheduler/           调度计划、运行锁、重试和额度控制
commands/            同步、补录、重放、特征生成等入口
tests/               契约、集成、迁移、历史保留与时点测试
docs/                架构、字段、来源能力、运行和验收说明
```

Collector 负责请求、分页、限流和返回原始观测，不直接拼接数据库 SQL；Normalizer 尽量是从原始载荷到标准记录的纯转换；Repository 负责事务、幂等和持久化；质量与实体映射是独立步骤。

初期采用单机批处理架构。PostgreSQL + 原始文件档案 + 离线特征输出足够。分布式队列、图数据库、向量数据库及独立在线 Feature Store 服务等待实际需求。

## 5. 原始数据与时间版本是第一优先级

每次请求产生可追溯的观测记录。先保存原始响应，再解析；解析失败仍保留载荷以供离线重放。

建议路径按来源、日期与唯一观测 ID 组织，例如：

`raw/<source>/<UTC-date>/<observed-at>_<observation-id>.json.gz`

保留响应正文的可还原内容；HTTP 请求失败和非 JSON 响应也应记录状态及适当的载荷引用。路径示例仅说明组织方式，不创建伪造业务数据。

原始记录至少包含：来源、端点、脱敏请求参数、请求 ID、抓取时间、HTTP 状态、payload 路径/URI、内容哈希、载荷格式。解析器与 Schema 版本另有记录。文件采用原子写入，数据库引用与处理状态支持失败恢复。

相同内容可按哈希共享载荷，但每次真实抓取的观测记录应保留。重试同一逻辑操作应幂等，避免生成重复事实或重复特征。

时间模型至少区分：

- `event_time`：事件发生时间。
- `source_published_at`：来源公开时间；未知时保留空值。
- `first_observed_at` / `observed_at`：本系统首次观察时间及本次观察时间。
- `ingested_at`：入库时间。
- `valid_from` / `valid_to`：事实适用区间。
- `supersedes_id`：事实修订关系。

UTC 保存标准时间，PostgreSQL 使用具备时区语义的类型；保留解析所需的原始时间和来源时区。显示及调度默认 Asia/Shanghai，并允许配置。

区分两种回放模式：

1. `operational`：复现系统当时实际收到的数据，以实际观测时间和版本为边界。
2. `historical_reconstruction`：使用具有可信历史快照或公开时间的档案，明确记录假定获取延迟、依据和模式。

今天抓取的历史网页保留今天的观测时间。旧 SQLite 的行创建时间、比赛日期和事件日期都不直接充当每个字段的首次可见时间；迁移时标记时间来源与不确定性。

## 6. 统一 Schema 与 PostgreSQL 数据仓库

用有类型的模型和明确的版本管理实现统一 Schema。缺失比分、赔率或统计用 null 及缺失原因表达，避免以 0 冒充未知值。0:0 是合法赛果。

建议采用以下逻辑分层，可使用 PostgreSQL schema 或表名前缀表达：

- 原始层：不可变观测档案和处理状态。
- 规范化层：实体、来源映射、事实版本、赔率与统计历史。
- 特征层：按时点生成的特征值和运行清单。

核心实体与表至少覆盖：

| 表/实体 | 关键要求 |
|---|---|
| `competitions` / `seasons` | 联赛、杯赛、赛季身份与来源映射 |
| `matches` + 比赛版本 | 内部 ID、赛事、赛季、主客队 ID、开球时间、比赛状态、中立场、阶段性比分；改期和修订留历史 |
| `teams` | 稳定身份、名称、国家、球队类别；Elo 和排名另存时变表 |
| `players` | 球员身份及来源映射；所属球队需要时间语义 |
| `entity_source_map` | source + entity_type + source_id 到内部 ID 的映射，附确认状态和版本 |
| `team_aliases` / `team_mapping` | 已确认别名、语言、适用来源、上下文和匹配依据 |
| `team_statistics` | team_id、match_id 或统计窗口、指标、值、单位、provider、口径版本和可用时间 |
| `team_state_history` | Elo、排名、近期状态等派生结果及计算截止点、方法版本 |
| `odds_history` | 每次报价/快照，追加存储；按报价版本和观测记录实现幂等 |
| `injuries` / `availability_events` | 球员、球队、比赛范围、伤停/疑似/复出状态、原始证据和修订关系 |
| 阵容/比赛事件表 | 按实际已接入能力实现；事件 ID、阶段、时间、参与实体和修订 |
| `raw_data` / `raw_observations` | 原始载荷索引、观测、内容哈希和重放状态 |
| `quality_issues` | 规则、严重级别、原始证据、受影响记录、处理状态 |
| `pipeline_runs` / `collector_runs` | 配置摘要、各阶段计数、状态、错误分类、时间和额度统计 |
| `feature_snapshots` | 比赛、预测截止点、特征版本、信息模式、输入血缘和特征值 |

报价契约至少包括：

`match_id, provider, bookmaker, market_type, period, selection, line, decimal_price, source_timestamp, observed_at, raw_observation_id, settlement_rule`。

区分供应商与博彩公司；来源未给出 bookmaker 时明确未知，避免把聚合网站名称编造成实际博彩公司。

竞彩让球胜平负、亚洲让球、准确总进球和大小球分别建市场类型。负盘口线属于合法数值。开盘、收盘及变化量由序列派生，并记录定义；最早采集报价不自动等同真实开盘价。

xG、xGA、射门质量等保留供应商及定义，避免跨供应商无标记地平均或拼接。球员影响程度属于后续模型估计，不伪装成伤停原始事实。

使用版本化数据库 migration；关系、唯一约束、索引和事务围绕实际查询设计。幂等键需覆盖来源、实体、版本和观测语义，既避免重复插入，也保留真实更新。

## 7. 球队、球员与比赛实体解析

优先匹配来源稳定 ID 和人工确认映射。别名支持中文、英文简称和历史名称。

名字相似只是候选信号，结合国家、联赛、球队类别、对手、主客关系和合理时间窗口核验。男子、女子、青年及预备队显式区分。

匹配不确定时进入待确认队列，保留来源实体，避免静默强制合并。提供可重复执行的确认/纠错入口和审计记录。

比赛内部 ID 应稳定；开球时间变化时更新比赛版本，不因改期自动生成另一场比赛。对杯赛重复交锋、主客翻转、同日多场等情况进行检查。

## 8. 数据质量规则与失败处理

质量规则从统一模型建立时开始贯穿管道，不拖到接入全部来源之后。

必须覆盖：

- 必填球队、实体关系和主客队重复。
- 时间解析、时区、比赛阶段和状态一致性。
- 比分类型、非负性、半场与全场关系；异常大比分作为可配置告警，不随意硬编码丢弃。
- 完赛缺比分、取消/延期误标完赛、历史赛果被修订。
- 赔率为空、非数、非正或不符合标准化十进制语义；极端合法报价与非法值分开处理。
- 盘口、周期、选项数量及结算规则一致性。
- 来源 ID 冲突、别名冲突、赛程匹配不确定。
- 数据新鲜度、字段覆盖和跨来源赛果不一致。
- 重复记录、修订记录和缺失原因。

区分硬错误、可恢复异常和质量警告。失败记录进入隔离或待处理区，保留原始引用和规则版本；报告有效、隔离、跳过和失败数量。隔离造成的样本覆盖变化也要报告。

Collector 实现明确超时、分页、有限重试、指数退避、Retry-After、供应商额度和分类错误。来源局部失败应允许其他独立来源继续执行；数据库故障则明确影响哪些下游阶段。

## 9. PostgreSQL 渐进迁移

使用 PostgreSQL 作为新平台主存储。保留现有 SQLite 文件及旧入口作为迁移参照。

迁移交付：

1. 版本化 migration、环境配置模板、健康检查。
2. 旧 SQLite 到 PostgreSQL 的可重跑导入命令。
3. 原始 ID 到内部 ID 映射、旧记录来源标记与时间不确定性标记。
4. 行数、唯一性、关键字段及抽样记录对账报告。
5. 部分失败恢复和回滚说明；采用新增和切换方式，保留原数据。

先检查现有 PostgreSQL 或容器运行条件，避免安装重复数据库。可提供 Docker Compose 作为开发启动方式，但以本机实际运行验收为准。数据库未就绪时显示对应状态，不自动切到 SQLite 后宣称 PostgreSQL 已通过。

## 10. 离线 Feature Store

第一版实现稳定的数据接口和按时点构建的特征表/Parquet 输出，无需先部署独立 Feature Store 产品。

特征主键与清单至少含：

`match_id + prediction_cutoff + feature_version + information_mode + input_manifest_hash`。

提供可等价调用的接口：

- `get_features(match_id, as_of, feature_version, information_mode)`
- 按联赛、赛季和预测提前量批量生成特征。
- 重放相同输入清单，得到一致结果。

首批特征：

- Elo 及主客实力差：按截至时点已可知的已完赛结果顺序更新，记录算法参数和版本。
- 最近 N 场表现、进失球、主客场表现、休息天数：仅使用合法历史窗口。
- 同时点胜平负市场概率及报价新鲜度：赔率完整且语义一致时计算，缺失则标记。
- xG/xGA 滚动统计：实际完成对应来源接入后启用；缺数据保留缺失原因。

为每个特征保留输入记录/快照引用、计算时点、窗口和缺失标记。派生特征的可用时间由实际输入决定。

结果标签与特征分离。赛后 xG、最终排名、目标比赛赛果、预测时点之后的阵容/伤停/赔率均不进入更早时点的特征。球赛标签需明确实际揭晓时间。

Elo 和近期表现需要尽可能完整的目标联赛历史；spftll 的足彩入选比赛集合不自动代表完整联赛赛程。统计每队历史覆盖，覆盖不足时标记，不将缺赛解释为没有比赛。

## 11. 调度和命令行

先完成 `run-once` 的真实端到端执行，再启用持久调度。

支持下列能力，可结合现有 CLI 设计等价子命令：

- 同步未来赛程。
- 补录指定日期/赛季的历史赛果。
- 刷新指定比赛或开球窗口内的赔率、阵容、伤停。
- 从原始载荷重新解析入库，避免重复请求外站。
- 构建指定预测时点的离线特征。
- 查看某次运行、某个来源和数据新鲜度。

默认 `python main.py` 在清楚的工作目录和配置下运行一次完整管道，并输出真实状态。旧 CLI 保持兼容，必要时通过独立平台入口过渡并写清迁移方式。

调度配置包括：

- 每日历史赛果回补与修订检查。
- 每日未来赛程更新。
- 按实际开球时间计算赛前赔率、阵容、伤停刷新计划。
- 时区、错过任务的补跑策略、并发锁、幂等键、超时及供应商额度。

在本机 Windows 环境采用可运行的调度方式，优先复用已有任务计划机制或提供经过验证的调度入口。明确区分“调度配置已生成”“手动触发通过”“已注册并处于自动执行状态”。注册后核验任务状态；不依赖隐藏在交互终端中的临时循环宣称长期运行完成。

每日时段和赛前刷新频率配置化，按源更新频率及额度确定，不为展示实时性高频无效轮询。

## 12. 状态报告与配置

同时提供终端摘要和机器可读运行清单。所有数字来自本次真实运行或明确的数据库查询，不硬编码示例比赛数。

每个来源分开报告：

- 实现状态。
- 固定样本/契约测试状态。
- 真实联网状态。
- 本次入库和特征影响。
- 已验证日期、联赛、赛季与字段范围。

状态至少区分 `OK`、`PARTIAL`、`NO_DATA`、`SKIPPED_DISABLED`、`NEEDS_CREDENTIALS`、`NEEDS_DATABASE`、`RATE_LIMITED`、`FAILED`。仅请求、解析、质量处理和预期入库链路按定义成功时，显示对应成功状态。

摘要包含 run_id、时间、来源请求数、原始观测数、有效/隔离/跳过/失败记录数、实体待确认数、报价写入数、特征生成数、数据库状态、运行耗时及适用时区的今日比赛数。

环境变量按实际服务统一命名，例如 `DATABASE_URL`、`FOOTBALL_DATA_API_TOKEN`、`API_FOOTBALL_KEY`、`THE_ODDS_API_KEY`；遵循实际官方认证方式。配置模板只保留空值或说明，日志、请求摘要和共享载荷中的认证信息脱敏。

## 13. 按依赖组织交付与验收

以下编号用于划分交付与验收，不代表所有工作串行执行。现状核对后，无冲突的来源适配、契约、仓库内部实现、特征计算、CLI 和测试并行推进；只在消费实际接口或数据时等待对应输入。每个可运行交付报告修改文件、修改原因、数据流变化、验证命令与实际结果。

| 阶段 | 交付 | 验收门槛 |
|---|---|---|
| Step 1 | 现状审计、来源能力矩阵、数据库与凭据状态、增量计划 | 明确已有能力与真实缺口，确定试点联赛和接入优先级 |
| Step 2 | 保留 spftll，接入原始观测档案和统一采集结果协议 | 旧入口回归通过；一批真实采集可保留和重放原始载荷 |
| Step 3 | 统一 Schema、时间语义、实体映射、基础质量规则 | null/比分/市场类型/冲突映射/时间等关键契约验证通过 |
| Step 4 | 第二来源适配与归一化 | 样本验证与真实联网验收分开，输出两源可对齐的真实记录 |
| Step 5 | PostgreSQL、migration、repository、旧数据导入 | 数据库集成验证、导入重跑和对账通过，原数据仍可读取 |
| Step 6 | 第三来源真实接入与追加报价/事件历史 | 验证真实增量数据与修订/历史保留，明确覆盖和缺口 |
| Step 7 | 完整质量隔离、时点特征、CLI 与调度 | 时间回放、幂等、故障恢复、小规模真实闭环和调度状态均有证据 |

测试围绕风险和契约设计，不以文件覆盖率代替正确性。最低关键验证包括：

1. 原有 spftll 采集与解析行为兼容。
2. 同一操作重跑不重复事实，真实新观测与历史报价得到保留。
3. 新消息与赛后结果不改变更早 `operational` 时点的特征。
4. 同源实体 ID 稳定，别名冲突和改期得到正确处理。
5. 延期、取消、完赛、半场与全场、0:0 等状态语义正确。
6. PostgreSQL migration 与 SQLite 导入可重跑，对账可解释。
7. 网络超时、429、部分来源失败、解析失败、数据库事务失败可恢复。
8. 相同输入清单及特征版本重放一致，xG 缺失不生成虚假值。
9. 调度重复触发不并发重复写入，改期后的赛前计划可调整。

端到端验收至少展示：同一真实比赛两次不同观测 → 原始档案 → 标准记录/历史报价 → 指定时点特征 → 真实运行报告。没有发生价格变化时如实展示相同报价及不同观测；变化场景使用明确标注的测试夹具验证，不虚构真实变盘。
